# DNS Server Test

A cache-backed UDP DNS server for reproducible experiments. It replays responses captured
by `dns-client-test` without querying an upstream DNS resolver.

Тестовый UDP DNS-сервер для воспроизводимых экспериментов. Воспроизводит ответы из кеша,
записанного `dns-client-test`, без обращения к вышестоящему DNS-резолверу.

## Описание

Вместо рекурсивного разрешения имен сервер загружает cache-файл, созданный `dns-client-test`, индексирует сохраненные ответы по домену и возвращает соответствующий DNS-пакет клиенту.

Один запуск сервера использует один cache-файл. Это намеренно оставляет реализацию простой: для `A` и `HTTPS` используются отдельные cache-файлы, поэтому серверу не требуется общий индекс `(domain, QTYPE)`.

## Разработка и проверка изменений

**Опорные символы для изменения поведения:**

1. `get_domain_from_packet`, `domain_find_hash` - разбор имени в запросе и индексирование кеша;
   ключ поиска по домену не включает QTYPE.

**Основные точки изменения:**

- `src/dns_server_test.c` - загрузка кеша и формирование DNS-ответов по полученным запросам;
- `include/dns_server_test.h` - объявления и настройки сервера;
- `CMakeLists.txt` - сборка и интеграция зависимости `hashmap`.

**Контракт кеша:** `dns-client-test` записывает подряд записи вида
`domain\0` + `int32_t` размера пакета + исходный бинарный DNS-ответ.
Сервер загружает файл целиком и хранит ссылки на данные внутри этого буфера.
Смена формата, представления длины или срока жизни буфера требует согласованных
изменений в обоих проектах. `int32_t` записан клиентом в нативном порядке
байт, а сервер читает его через указатель на `int32_t` без копирования в
выровненную переменную. Формат не гарантирует переносимость между
архитектурами с разным порядком байт или требованиями к выравниванию.
Парсер кеша предполагает корректные записи и не
предназначен для чтения недоверенных файлов без дополнительной валидации.

**Граница доверия к кешу:** внутри цикла загрузки `strlen()` ищет
конец имени домена, затем непосредственно читается `int32_t` длины
и выполняется переход на эту длину. Проверок, что завершающий нулевой
байт, поле длины и весь DNS-пакет лежат внутри прочитанного буфера, нет.
Используйте только доверенные, целые файлы, созданные совместимым клиентом;
для приёма произвольных файлов необходимо добавить поэтапную проверку
каждого поля и границы записи до разыменования указателей.

**Поток запроса:** UDP-пакет должен содержать один вопрос DNS. Сервер извлекает
домен, находит сохранённый ответ и заменяет в нём ID транзакции на ID запроса.
При отсутствии записи ответ не отправляется. Ключ индекса содержит домен,
но не QTYPE: используйте кеш, соответствующий типу запросов клиента.
Сервер не анализирует QTYPE и не создаёт новых отрицательных DNS-ответов.
Однако сохранённый `dns-client-test` корректный ответ с отрицательным RCODE
(например, `NXDOMAIN`) может быть возвращён как обычный кешированный пакет:
при отправке меняется только ID транзакции. Все остальные поля сохранённого
ответа, в том числе TTL ресурсных записей, передаются без пересчёта по
прошедшему времени. Это **воспроизведение тестовой записи**, а не кеш
DNS с актуализацией времени жизни; его нельзя использовать как
источник свежих ответов. Для поддержки TCP, проверки
типа запроса и генерации ответов при отсутствии домена нужны изменения кода,
а не только другое имя cache-файла.

**Файлы сборки:** `CMakePresets.json` содержит профили конфигурации CMake, а `CMakeLists.txt` определяет зависимости и исходники DNS-сервера. Смена формата кеша требует изменений и в соседнем DNS-клиенте.

**Проверка изменений:** При изменении формата кеша сверяйте чтение здесь
с записью в `src/dns_client_test.c` соседнего проекта `dns-client-test`. При изменении обработки
запроса отдельно проверяйте корректный вопрос, неизвестный домен, ID ответа
и соответствие типа запроса выбранному кешу. В репозитории нет собственного
набора автоматизированных тестов; выполнение сетевых проверок требует стенда.

## Сборка

```sh
git submodule update --init --recursive
cmake --preset release
cmake --build --preset release
```

Исполняемый файл:

```text
build/release/dns-server-test
```

## Использование

```text
Required:
  -l IPv4:port       Адрес прослушивания

Optional:
  -c path            Путь к cache-файлу, по умолчанию cache.data
```

Старый вариант остается рабочим:

```sh
./build/release/dns-server-test -l 127.0.0.1:5353
```

В этом случае сервер читает `./cache.data`.

Для нового `A` cache:

```sh
./build/release/dns-server-test \
    -l 127.0.0.1:5353 \
    -c cache-A.data
```

Для `HTTPS` cache:

```sh
./build/release/dns-server-test \
    -l 127.0.0.1:5353 \
    -c cache-HTTPS.data
```

### Подготовка кеш-файла

Например, `A` dataset можно собрать так:

```sh
dns-client-test \
    -f domains.txt \
    -d 1.1.1.1:53 \
    -r 300 \
    -A \
    --save
```

Будет создан:

```text
cache-A.data
```

Для `HTTPS`:

```sh
dns-client-test \
    -f domains.txt \
    -d 1.1.1.1:53 \
    -r 300 \
    -H \
    --save
```

Будет создан:

```text
cache-HTTPS.data
```

Бинарный формат cache-файла не изменен по сравнению с исходным `cache.data`.

## Почему сервер не хранит ответы A и HTTPS вместе

Клиент намеренно создаёт отдельные datasets:

```text
cache-A.data
cache-HTTPS.data
```

Поэтому серверу достаточно старой простой модели:

```text
domain -> saved DNS response
```

Для replay нужно запускать сервер с cache-файлом того же типа, который затем запрашивает клиент. Например, `cache-HTTPS.data` используется вместе с клиентом в режиме `-H`.
